## 1. Моделирование процессов (блок 05)

*Источник: course-materials/05-xx.*

### 1.1 Модель процесса
- **Виды моделей:** бизнес-процесс (организация), системный процесс (компоненты системы), порядок выполнения программы.
- **Уровни:** контекстный (окружение, участники, входы/выходы) → операционный (подпроцессы, последовательность, варианты) → системный (кто выполняет, условия, время, результат).
- Системный аналитик определяет, **какие процессы автоматизировать** для выполнения задач заинтересованных лиц.

### 1.2 Элементы модели процесса
- **Семь элементов:** действие (activity), событие (event), поток (flow), точка принятия решения, роль (participant), данные (data), ссылка (link).
- Событие: стартовое, конечное, промежуточное. Действие — задача (глагол) или подпроцесс (существительное).

### 1.3 Диаграмма бизнес-процесса (BPMN)
- **Пул и дорожки:** пул — группа участников, дорожка — роль. Задачи (прямоугольник), подпроцесс (+), события (круги: тонкий — старт, жирный — конец, двойной — промежуточное). Шлюзы: X (исключающее ИЛИ), + (параллельное И), O (неисключающее ИЛИ).
- **Важно:** процесс должен иметь логическое завершение для всех веток; если специалист не найден — возврат к поиску или уведомление, а не обрыв на «добавили в базу».

### 1.4 Диаграмма деятельности (UML Activity)
- Нотация UML для описания потоков работ (действия, решения, ветвления).

### 1.5–1.8 Границы процесса, этапы, роли, SIPOC
- SIPOC: Suppliers, Inputs, Process, Outputs, Customers — определение границ процесса.
- Роли и управление доступами для участников процесса.

### 1.9–1.10 UML, диаграмма прецедентов (Use Case)
- Use Case — сценарии использования. Актор (человек или система), прецеденты, связи include/extend.

### 1.11–1.12 Чтение Use Case, алгоритм построения
- Чтение диаграмм прецедентов; алгоритм построения (первичный актор ≠ система).

### 1.13 Диаграмма последовательности (Sequence) — основы
- Участники, линии жизни, сообщения (синхронные/асинхронные/ответные).

## 3. Программные интерфейсы (блок 09)

*Источник: course-materials/09-xx.*

### 3.1 От доменной модели к API: слои, ресурсы и DTO
- **Слои:** доменный (бизнес-логика) → прикладные сервисы (use-case) → транспортный (Web/API: десериализация DTO, валидация, аутентификация, маппинг). DTO — плоские, стабильные, минимальные структуры для границы. Ресурс в API ≈ агрегат в домене.

### 3.2 Стили взаимодействия приложений
- Синхронный / асинхронный. Стили: файловый обмен, общая БД, RPC, обмен сообщениями (MOM). Факторы: доставка, связанность, сложность, формат данных, задержка.

### 3.3 Обмен сообщениями (Messaging)
- Сообщение = заголовок + тело. Канал, store-and-forward. Асинхронность, низкая связанность.

### 3.4 RPC и основы API
- Запрос → обработка → ответ. API: endpoint, методы, параметры, формат данных.

### 3.5 Сетевые модели и протоколы
- OSI (эталон), TCP/IP (прикладной — HTTP; транспортный — TCP; сетевой — IP; канальный).

### 3.6 HTTP-запрос и ресурсы
- Ресурс — абстракция с URI. Сериализация/десериализация. Стартовая строка (метод, путь, версия), заголовки, тело.

### 3.7 HTTP-ответ
- Код состояния (1xx–5xx), заголовки, тело. Примеры: 200 OK, 404 Not Found, 500 Internal Server Error.

### 3.8 Параметры HTTP
- Path, query, header, body. В ответе: status, headers, body.

### 3.9 JSON
- Объект `{}`, ключ–значение, типы: string, number, boolean, array, null, object.

### 3.10 XML и SOAP
- XML — теги, атрибуты, вложенность. SOAP — фреймворк обмена на XML.

### 3.11 XML-схема и пространства имён
- XSD для валидации структуры. Namespaces для избежания конфликтов имён.

### 3.12 Элементы SOAP API
- SOAP Envelope: Header (опционально), Body (обязательно). soap:Fault для ошибок. WSDL — описание сервиса.

### 3.13 Сравнение REST и SOAP
- REST: ресурсы, HTTP-методы, stateless, JSON/XML. SOAP: операции, только XML, строгая спецификация. REST — архитектурный стиль; SOAP — протокол.

### 3.14 Документирование API
- Swagger (OpenAPI) для REST, WSDL для SOAP. Postman, Redoc.

### 3.15 Диаграмма последовательности (UML Sequence)
- Акторы, объекты, линии жизни, сообщения (синхрон/асинхрон/ответ), фреймы (alt, opt, loop, ref). Иерархия: UI → API → Backend → DB.

### 3.16 Алгоритм проектирования sequence
- Участники → таблица взаимодействий (порядок, действие, отправитель, получатель, тип REST/SOAP, метод) → базовый сценарий → фреймы (alt/loop/par) → детализация (POST /booking, 200 OK).

## 4. Работа с репозиториями и контроль версий

*Продолжать конспектирование с этой темы. Вы открываете каждый урок на платформе (мышкой) → пишете «готово» → агент дополняет конспект ниже.*

### 4.1 Версионирование в разработке приложений
*Спринт 10 | Тема 1/4: Система контроля версий Git и парадигмы разработки | Урок 1/4*

- **Зачем нужен контроль версий:** разработчикам нужно параллельно и независимо работать над одной программой и иметь инструмент для версионирования.
- **Subversion** — решение проблемы централизованного хранения кода (до Git).
- **Эволюция Git:**
  - *Распределённое управление* — любой разработчик работает со своей копией проекта как с основным репозиторием, затем синхронизирует изменения с остальными.
  - *Быстрота* — большинство операций выполняются локально: переключение веток, история коммитов, создание и откат изменений без задержек.
- **Основные термины:**
  - **Репозиторий** — local (на компьютере разработчика) или remote (на сервере/в облаке).
  - **Коммит** — фиксация изменений; содержит: дату, автора (email), текстовый комментарий, хеш-сумму.
  - **Ветка** — параллельная линия разработки.
- *Дополнительно:* [История появления Git](https://git-scm.com/book/ru/v2/Введение-Краткая-история-Git).

### 4.2 Парадигмы разработки в Git
*Спринт 10 | Тема 1/4: Система контроля версий Git и парадигмы разработки | Урок 2/4*

- **Зачем нужны парадигмы:** репозиторий, как и исходный код, требует чёткой организации процесса. Подходы определяют: как создаются ветки, для чего каждая нужна, когда они сливаются с основной. У всех подходов есть плюсы и минусы.
- **Две популярные модели:** Git Flow и Trunk-Based Development. Обе хороши; выбор зависит от процесса разработки.

**Git Flow — структурированный подход:**
- Известная модель ветвления. Подходит для больших проектов: с длинными циклами выпуска, со сложной архитектурой, со строгим контролем версий.
- **Ветки:** `master`/`main`, `develop`, `feature`, `release`, `hotfix`.
- **Задачи:** планировать релизы; следить за качеством кода; организовывать процесс прозрачно и понятно.

**Trunk-Based Development — скорость и гибкость:**
- Альтернативная модель: короткоживущие ветки, частые слияния с основной веткой, меньше формальностей.

### 4.3 Ветвление
*Спринт 10 | Тема 1/4: Система контроля версий Git и парадигмы разработки | Урок 3/4*

Продолжение темы Git Flow и Trunk-Based Development — практика работы с ветками.

**Управление ветками:**
- **git branch** — просмотр, создание веток. Есть дополнительные опции для просмотра.
- **git switch** — переключение между ветками (современная команда):
  - `git switch my-branch` — перейти на ветку;
  - `git switch -` (или `--previous`) — вернуться на предыдущую ветку (удобно при временном переключении, например для push).
- **git checkout** — альтернатива для переключения (старая, многофункциональная команда); для смены ветки предпочтительнее `git switch`.

**git branch —show-current** — показывает текущую ветку.

**Осторожно:** при несохранённых изменениях переключение может не пройти. Флаг `--discard-changes` принудительно отбрасывает изменения — использовать аккуратно, лучше сначала закоммитить.

**Удаление веток:**
- `-d` — обычное удаление (если ветка слита);
- `-D` — принудительное удаление.

**Создание ветки:** опция `-c` для создания от текущего состояния; `-b` — создать и переключиться.

### 4.4 Разница между слиянием и перебазированием
*Спринт 10 | Тема 1/4: Система контроля версий Git и парадигмы разработки | Урок 4/4*

**Ключевое различие:**
- **merge** сохраняет историю коммитов и слияний; полезен для публичных веток — всегда видно, как изменения попали в ветку.
- **rebase** переписывает историю, не создаёт отдельного коммита слияния; удобен для личных/локальных веток, даёт линейную историю.

**Git Merge:**
- Создаёт коммит слияния (при необходимости). Может использовать fast-forward, если ветка не разошлась.
- **Опции:** `--ff-only` (только fast-forward, иначе ошибка); `--no-ff` (всегда коммит слияния); `--squash` (объединить все коммиты в один перед слиянием); `-m` (сообщение для коммита); `--no-commit` (не коммитить сразу, проверить состояние); `--abort` (отменить слияние до коммита).
- **Конфликты при merge:** нужно разрешить вручную, затем закоммитить.

**Git Rebase:**
1. Находит общего предка двух веток.
2. Вставляет коммиты текущей ветки поверх целевой (сливаемой) ветки.
3. Переписывает историю — ветка становится линейной.
- **Опции:** `--continue` (после разрешения конфликтов); `--abort` (отменить rebase); `-i` (интерактивный режим — задать порядок коммитов); `--skip` (пропустить коммит при конфликтах); `--ignore-date` (текущая дата для коммитов).

*Дополнительно:* [Тонкости благополучного git-merge](https://habr.com/ru/articles/...) на Хабре.

### 4.5 Работа с удалёнными репозиториями
*Спринт 10 | Тема 2/4: Продвинутая работа с удалёнными репозиториями и тегами и псевдонимы | Урок 1/3*

Git — распределённая система: код на удалённом сервере, у каждого члена команды локальная копия.

**Зачем нужны удалённые репозитории:** совместная работа, резервное копирование, управление версиями, интеграция CI/CD, обсуждения и код-ревью.

**Клонирование:** `git clone [опции] <URL> [папка]`. Флаги: `-b` (выбрать ветку), `--depth N` (только последние N коммитов), `--single-branch`, `--recurse-submodules`, `-o` (имя remote, по умолчанию origin).

**Отправка:** `git push [опции] [remote] [ветка]`. Флаги: `-f` (принудительно — осторожно: потеря данных других, конфликты); `-u` (связать локальную и удалённую ветки); `--dry-run`; `--tags`; `--all`.

**Получение без обновления (fetch):** `git fetch` — загружает изменения, не мержит. Флаги: `--all`, `--prune` (убрать ссылки на удалённые ветки), `--tags`, `--dry-run`.

**Получение с обновлением (pull):** fetch + merge. Флаги: `--rebase`, `--no-edit`, `--all`.

**Настройка remote:** `git remote add <имя> <URL>`; `git remote rename <старое> <новое>`; `git remote set-url <имя> <новый URL>`; `git remote` (просмотр); `git remote remove <имя>`.

**Несколько удалённых репозиториев:** резервное копирование, подмодули, разные команды/платформы, dev/test/deploy, версии. Подходы: понятные имена (origin, backup, staging), чёткое разделение задач, консистентность.

### 4.6 Работа с тегами (Tags)
*Спринт 10 | Тема 2/4: Продвинутая работа с удалёнными репозиториями и тегами | Урок 2/3*

Теги в Git — инструмент управления версиями; отмечают важные точки в истории (релизы, значимые изменения).

**Свойства тегов:**
- **Неизменяемость** — фиксируют коммит (v1.0, v2.0-beta).
- **Читаемость** — понятные имена (release-2023-10, test-5.4.0).
- **Управление версиями** — отслеживание релизов, откат к версии.
- **Важные моменты** — конец фазы разработки, старт тестирования, выход функции.
- **CI/CD** — указатель на коммит для автоматической сборки и развёртывания.
- **Документация** — быстрый поиск нужной версии.

**Виды тегов:**
- **Легковесные** — простой указатель на коммит: `git tag <имя>`.
- **Аннотированные** — с метаданными, сообщением: `git tag -a <имя> -m "<сообщение>" [хеш]`. Флаг `-a`/`--annotate`, `-m` — сообщение (без него откроется редактор). Можно указать хеш коммита (подойдёт и короткий).

**Конфликт имён (тег/ветка):**
- Ясное именование — префиксы: v1.0 для тегов, feature/ для веток.
- Проверять существующие объекты перед созданием.
- Полные ссылки: `refs/tags/<имя>`.

**Команды:**
- **Просмотр:** `git tag` — список всех тегов.
- **Удаление локально:** `git tag -d <имя>`. Удаление в remote: `git push <remote> --delete refs/tags/<имя>`.
- **Отправка:** `git push [опции] [remote] [тег]`. `git push origin --tags` — все теги.
- **Редактирование:** `git tag -a -f <имя> -m "msg"` — флаг `-f` перезаписывает тег (как `--force`).
- **Переключение на тег:** `git checkout <тег>` или `git switch --detach <тег>` — перейти в detached HEAD на коммит тега.

### 4.7 Псевдонимы (Aliases)
*Спринт 10 | Тема 2/4: Продвинутая работа с удалёнными репозиториями и тегами и псевдонимы | Урок 3/3*

**Что такое:** псевдонимы (aliases) — короткие имена для команд Git. Можно задать свою команду вместо одной или нескольких стандартных.

**Зачем нужны:** упрощение длинных команд, меньше опечаток, персонализация, более понятные имена.

**Пример:** вместо `git status` — `git st` (если задать псевдоним `st`).

**Создание:** `git config --global alias.<имя> <команда>`. Команда может быть: одна команда Git (push, status), строка с командами (в кавычках), внешняя программа.

**Просмотр:** `git config --get-regexp alias` — все псевдонимы.

**Редактирование:** изменить в `~/.gitconfig` или задать заново.

**Удаление:** `git config --global --unset alias.<имя>`.

**Практика:** Исправить команду добавления псевдонима — `git alias lg = log --oneline --graph` → `git config --global alias.lg "log --oneline --graph"`.

### 4.8 Интерактивное индексирование
*Спринт 10 | Тема 3/4: Продвинутая работа с коммитами | Урок 1*

**Микрокоммиты** — небольшие, тематически целостные коммиты. Не «минимальные», а содержащие необходимый и достаточный набор изменений, сгруппированных по смыслу.

**Зачем разбивать на микрокоммиты:** упростить ревью, облегчить откат, улучшить поиск ошибок (проще найти, в каком коммите ошибка).

**Интерактивное индексирование** — команда `git add -p` (или `--patch`). Добавление изменений по фрагментам (hunks) с выбором:
- **y** — добавить фрагмент в индекс;
- **n** — пропустить фрагмент;
- **s** — разделить фрагмент на более мелкие части;
- **e** — отредактировать фрагмент вручную;
- **q** — выйти без дальнейших изменений.
