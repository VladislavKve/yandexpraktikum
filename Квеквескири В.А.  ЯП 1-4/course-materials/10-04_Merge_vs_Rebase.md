# Разница между слиянием и перебазированием
**Спринт 10/13 | Тема 1/4: Система контроля версий Git и парадигмы разработки | Урок 4/4**

В прошлом уроке — работа с ветками. Ещё одна ключевая операция — объединение веток: **merge** (слияние) и **rebase** (перебазирование).

## Git Merge
- **merge** сохраняет историю коммитов и слияний. Полезен для публичных веток — всегда понятно, как изменения попали в ветку.
- При отсутствии конфликтов создаётся новый коммит слияния (или fast-forward, если ветка не разошлась).

### Конфликты при merge
При конфликтах Git останавливается; нужно разрешить конфликты вручную, добавить файлы, завершить коммит.

### Полезные опции команды git merge
- `--ff-only` — слияние только через fast-forward; если невозможно — ошибка.
- `--no-ff` — отключает fast-forward, создаёт отдельный коммит слияния.
- `--squash` — объединяет все коммиты сливаемой ветки в один перед слиянием.
- `-m` — сообщение для коммита слияния.
- `--no-commit` — не создавать коммит сразу, позволить проверить состояние.
- `--abort` — отменить слияние до коммита (например, при неверно разрешённых конфликтах).

## Git Rebase
- **rebase** переписывает историю, избегает дополнительных коммитов. Удобен для личных/локальных веток, где история не критична. Даёт линейную историю.
- Как работает:
  1. Git находит общего предка двух веток.
  2. Git вставляет все коммиты текущей ветки поверх коммитов целевой ветки.
  3. Git переписывает историю — ветка становится линейной.

### Опции rebase
- `--continue` — после разрешения конфликтов продолжить rebase.
- `--abort` — отменить rebase.
- `-i` (interactive) — интерактивный режим, задать порядок и обработку коммитов.
- `--skip` — пропустить текущий коммит при конфликтах.
- `--ignore-date` — установить текущую дату для коммитов.

## Итоги
- **merge** — сохраняет историю, подходит для публичных веток.
- **rebase** — линейная история, удобен для личных веток. Не применять к уже опубликованным коммитам.
