# Парадигмы разработки в Git
**Спринт 10/13 | Тема 1/4: Система контроля версий Git и парадигмы разработки | Урок 2/4**

## Введение
Как и исходный код, репозиторий нуждается в том, чтобы процесс разработки был чётко организован. Для этого существуют разные подходы. Они определяют, как создаются ветки, для чего нужна каждая из них, в какой момент они сливаются с основной и т.д. У всех подходов есть свои плюсы и минусы.

В этом уроке рассматриваются две популярные модели: **Git Flow** и **Trunk-Based Development**. Обе модели хороши — выбирать нужно в зависимости от процесса разработки.

## Модель Git Flow. Структурированный подход
Git Flow — один из самых известных и широко применяемых подходов к управлению ветвлением. Используется в больших проектах:
- с длинными циклами выпуска;
- со сложной архитектурой;
- со строгим контролем версий.

### Основные ветки
- `master` или `main` — основная ветка, стабильный код
- `develop` — ветка разработки
- `feature` — ветки для новых функций
- `release` — ветки подготовки релизов
- `hotfix` — срочные исправления

### Задачи модели
- планировать релизы;
- следить за качеством кода;
- организовывать процесс так, чтобы каждый шаг был прозрачным и понятным.

## Модель Trunk-Based Development. Скорость и гибкость
Альтернативная модель: короткоживущие ветки, частые слияния с основной веткой (trunk), меньше формальностей. Подходит для проектов с непрерывной интеграцией и короткими циклами.

## Итоги
Выбор парадигмы зависит от размера команды, частоты релизов и требований к контролю. Git Flow — для структуры; Trunk-Based — для скорости.
